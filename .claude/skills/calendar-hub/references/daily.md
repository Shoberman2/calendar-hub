# Daily reconciliation

Use this only after the user asks for recurring maintenance. Inspect existing jobs before creating one. Agree on local timezone and time; prefer one job per user. Use the assistant's supported scheduling feature and verify its saved active status and next run. The host may require an awake, unlocked machine and signed-in accounts. Do not install an unsupervised browser daemon or a public GitHub Actions job with calendar secrets as a fallback.

Adapt this prompt to the user's recorded scope:

> Continue Calendar Hub using the existing local status and approvals. Inspect source and destination calendars for the upcoming 90 days, plus class meetings through the verified term end. Include all recorded enrolled courses and the user's selected personal/work sources. Compare source IDs, recurrence instances, event times/timezones, cancellations, and last-modified data where available. Search authorized invitation mail only for the relevant new/changed meeting scope. Add only confirmed missing events under existing authorization; update only events this workflow created and only when the source is unambiguous. Do not send mail, RSVP, add attendees, publish calendars, delete entries, or expand permissions. Flag cancellations and conflicts for review. Avoid duplicate native/subscribed views. Preserve the user's category colors. Record last successful checks separately from source refresh times; a stale feed is not proof that an event is absent. If authentication, device access, or user clarification is needed, record the blocker and notify. Stay quiet when unchanged; notify only meaningful changes, failures, or required action. Never expose private links or credentials.

Record scheduler identifier, timezone, run time, access dependencies, and verification in `.calendar-hub/status.md`. On a new semester, re-check enrollment and date bounds rather than extending old class events. If the environment cannot schedule work, provide this prompt for manual execution and mark automation unavailable.
